Put the IDS in the traffic path

Installing the root CA on a client does not route its traffic through this machine. It only makes the client trust the certificates this IDS forges, once traffic is already flowing through it. Before expecting to see decrypted flows in /dashboard, the client's traffic must actually pass through this host. Pick the topology that matches your network.

The client never needs to know this host's IP or port. From the client's perspective it makes an ordinary HTTPS connection to example.com:443. The interception is transparent — the network layer rewrites the destination before the packet leaves the client's subnet. No proxy settings, no PAC file, no client-side configuration beyond the CA trust step below.

About the port: the client always uses 443. The interceptor listens on SSL_INTERCEPT_PORT (default 8443) and the kernel rewrites the destination port from 443 to 8443 on the IDS host before the packet is ever seen by sslsplit. The client has no way to observe this rewrite, and no way to opt out of it — it happens below the transport layer. The only exception is Option 3 below, where the router performs the same rewrite and therefore needs the port written into its own DNAT rule.

Option 1 — Default gateway (simplest)

Point the client's default route at this host. All traffic flows through the IDS, which NATs it to the real internet and intercepts TCP/443 along the way. Works well for a single test client or a segment where every device can use the IDS as its gateway.

Step A — On the IDS host (Linux)

# 1. Enable IP forwarding
sudo sysctl -w net.ipv4.ip_forward=1
# Persist across reboots:
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-ids-forward.conf

# 2. NAT outbound traffic on the uplink interface.
#    Replace <UPLINK> with your real interface (eth0, ens18, enp1s0, ...).
sudo iptables -t nat -A POSTROUTING -o <UPLINK> -j MASQUERADE

# 3. Redirect inbound 443 into the interceptor.
sudo python -m ssl_inspect.iptables install

Step B — On the client

Choose the section that matches the client operating system. In all three the goal is the same: change the default gateway so it points at the IDS host's IP on the client's own subnet.

Linux client

# Change the default route.
# Replace <IDS_IP> with the IDS address on this client's subnet.
sudo ip route replace default via <IDS_IP>

# Verify.
ip route show default
# Should print: default via <IDS_IP> dev ...

Windows client (10 / 11 / Server)

:: Open cmd.exe as Administrator.

:: 1. Add a persistent default route via the IDS with a low metric,
::    so it wins over any DHCP-supplied default route.
::    Replace <IDS_IP> with the IDS address on this client's subnet.
route -p add 0.0.0.0 mask 0.0.0.0 <IDS_IP> metric 1

:: 2. Verify (the new 0.0.0.0 entry should appear near the top).
route print -4

:: To undo later:
route delete 0.0.0.0

GUI alternative: Control Panel → Network and Internet → Network Connections, right-click the active adapter → Properties → select Internet Protocol Version 4 (TCP/IPv4) → Properties → under Use the following IP address, set the Default gateway to the IDS IP.

macOS client

# Change the default route immediately.
# Replace <IDS_IP> with the IDS address on this client's subnet.
sudo route change default <IDS_IP>

# To make it persistent across reboots, update the network service.
# First list the services to find the one in use (usually "Wi-Fi" or "Ethernet"):
networksetup -listallnetworkservices

# Then set the router (default gateway) on that service:
sudo networksetup -setrouter "Wi-Fi" <IDS_IP>

# Verify.
netstat -rn | grep default

Why the MASQUERADE rule matters: without it, forwarded packets arrive at the IDS with the client's source IP and are dropped because the IDS does not route client addresses back to the internet. MASQUERADE rewrites the source to the IDS host's address on the way out, so the client's traffic reaches the real servers.

Option 2 — Transparent bridge (inline, no client reconfiguration)

Give this host two network interfaces and bridge them. Traffic physically traverses the IDS without any changes on the client. Common for dedicated appliances and for VMs with two virtual NICs. Requires bridge-utils and ebtables. 

# On the IDS host — bind two NICs into a bridge
sudo ip link add name br0 type bridge
sudo ip link set br0 up
sudo ip link set <NIC_IN> master br0
sudo ip link set <NIC_OUT> master br0

# Assign the IDS its own management IP on the bridge
sudo ip addr add <IDS_IP>/24 dev br0

# Bring up the NICs (no IP on the slaves themselves)
sudo ip link set <NIC_IN> up
sudo ip link set <NIC_OUT> up

# Redirect 443 into the interceptor (as usual)
sudo python -m ssl_inspect.iptables install

# Persist: bridge setup is normally done in /etc/network/interfaces
# or /etc/sysconfig/network-scripts/ifcfg-br0 depending on distro.

The client sees an ordinary switched network and needs no changes. Note that bridging disables the ability to bypass the IDS at the network level — if the IDS goes down, so does the link.

Option 3 — Upstream router DNAT

If you control the router between the clients and the internet, redirect TCP/443 on the router toward this host. The IDS stays off the traffic path for everything else. Best for mid-sized networks where a full bridge or gateway setup is not practical. 

# ---- On the ROUTER, not on the IDS ----
# Redirect any TCP/443 leaving the client subnet to the IDS.
# Replace:
#   <CLIENT_NET>  — the client subnet (e.g. 10.0.20.0/24)
#   <IDS_IP>      — this host's IP
#   <PORT>        — SSL_INTERCEPT_PORT from .env (default 8443)

sudo iptables -t nat -A PREROUTING \
  -s <CLIENT_NET> -p tcp --dport 443 \
  -j DNAT --to-destination <IDS_IP>:<PORT>

# Enable forwarding on the router if not already
sudo sysctl -w net.ipv4.ip_forward=1

# ---- On the IDS ----
# The redirect rule from ssl_inspect.iptables is NOT needed here, because
# the router has already DNAT'd 443 to the interceptor port. sslsplit
# simply listens on <PORT> and accepts the connections the router forwards.
# Do make sure the interceptor is running (SSL_DECRYPTION_ENABLED=true).

Watch out for double-redirect. If the IDS also runs python -m ssl_inspect.iptables install, packets arrive on the interceptor port, get redirected again to the same port, and the second REDIRECT rule does nothing. Remove the local redirect rule (python -m ssl_inspect.iptables remove) when using DNAT from an upstream router.

Other routers. The commands above are for Linux-based routers. pfSense and OPNsense use pf instead of iptables; MikroTik RouterOS uses /ip firewall nat. The underlying idea is the same in all three — DNAT any TCP/443 leaving the client subnet to <IDS_IP>:<PORT>.

Verifying that traffic is actually flowing through the IDS

After picking a topology, confirm the IDS is seeing intercepted packets before debugging certificates or the interceptor. 

# ---- On the IDS host ----
# Counter should increase as the client browses HTTPS sites.
sudo iptables -t nat -L PREROUTING -n -v
#   Look for non-zero packets/bytes on the REDIRECT rule

# sslsplit should be listening on the intercept port.
sudo ss -tlnp | grep <PORT>

# The connect log is written as sslsplit terminates connections.
sudo tail -f storage/sslsplit-connect.log
#   Each terminated flow emits one line while the client browses.

# ---- On the CLIENT ----
# Confirm the route points at the IDS (gateway topology only).
# Linux:
ip route show default
#   Must print `via <IDS_IP>` for Option 1 to work.
# Windows:
#   route print -4
# macOS:
#   netstat -rn | grep default

# Confirm the CA is trusted and openssl accepts the forged certificate.
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -issuer
#   Should print: issuer=C = ..., O = Enterprise AI IDS, OU = Network Security, CN = Enterprise AI IDS Root CA

If the iptables counters stay at zero, the client's traffic is not reaching this host. That is a routing problem — do not debug the interceptor or the CA first. If counters increase but the connect log stays empty, the packets are being redirected but sslsplit is not running or is listening on a different port.

Why this step is easy to miss. The CA trust step and the topology step are independent. Installing the CA without a topology change leaves the client connecting directly to the real server with the browser showing no warnings (because the real server's certificate is already trusted by the system store). Everything looks fine and nothing is being intercepted. This is the single most common reason people believe TLS interception "does not work."

Client trust installation

Use the Download CA (PEM) button in the Root certificate authority card above to save the file, then install it on every client that should be inspected. Without this step, browsers and applications will show certificate warnings on every HTTPS site. Pick the section that matches the client operating system.

Linux — Debian / Ubuntu

# Copy the CA into the system trust store
sudo cp enterprise-ai-ids-ca.crt /usr/local/share/ca-certificates/enterprise-ai-ids-ca.crt

# Refresh the trust store
sudo update-ca-certificates

# Verify (should print the CA subject)
awk -v cmd='openssl x509 -noout -subject' \
  '/BEGIN/{close(cmd)};{print | cmd}' \
  < /etc/ssl/certs/ca-certificates.crt | grep "Enterprise AI IDS"

Linux — Fedora / RHEL / CentOS

# Copy the CA into the anchors directory
sudo cp enterprise-ai-ids-ca.crt /etc/pki/ca-trust/source/anchors/

# Refresh the trust store
sudo update-ca-trust

# Verify
trust list | grep -A2 "Enterprise AI IDS"

Linux — Arch

sudo cp enterprise-ai-ids-ca.crt /etc/ca-certificates/trust-source/anchors/
sudo trust extract-compat

macOS

# Add the CA to the System keychain
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain \
  enterprise-ai-ids-ca.crt

# Verify
security find-certificate -c "Enterprise AI IDS" \
  /Library/Keychains/System.keychain

GUI alternative: open the .crt file with Keychain Access, add it to the System keychain, then double-click the entry and set When using this certificate to Always Trust. Administrator credentials will be required.

Windows (10 / 11 / Server)

# Run in an elevated PowerShell or cmd.exe

:: Import into the Local Machine Root store
certutil -addstore -f "ROOT" enterprise-ai-ids-ca.crt

:: Verify
certutil -store "ROOT" | findstr /I "Enterprise AI IDS"

GUI alternative: double-click the .crt file → Install Certificate → Local Machine → Place all certificates in the following store → Trusted Root Certification Authorities.

Firefox (all platforms)

Firefox uses its own certificate store and does not automatically trust the system store on Linux. Do one of the following. 

# Option 1 — trust the system store (simplest, works after any OS-level install)
1. Open about:config
2. Set security.enterprise_roots.enabled = true
3. Restart Firefox

# Option 2 — import the CA directly
1. Open about:preferences#privacy
2. Scroll to "Certificates" → click "View Certificates"
3. Go to the "Authorities" tab → click "Import…"
4. Select enterprise-ai-ids-ca.crt
5. Check "Trust this CA to identify websites" → OK

Chrome / Edge / Safari

Chrome and Edge on Windows and macOS use the operating system trust store, so the OS-level steps above cover them. Safari uses the macOS keychain. On Linux, Chrome uses the NSS store — run certutil against the NSS database if the system-wide install does not take effect: 

# Install libnss3-tools first (Debian/Ubuntu: nss-tools)
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n "Enterprise AI IDS" \
  -i enterprise-ai-ids-ca.crt
Verification checklist. After installing the CA on a client, open any HTTPS site (for example https://example.com):
  • No certificate warning. The padlock shows normally.
  • Issuer shows "Enterprise AI IDS Root CA". Click the padlock → Certificate → check the issuer.
  • The connection appears in the IDS. Open /dashboard → log search, and look for a row with decrypted=true and ml_skipped_no_features in the reasons column.

If the padlock shows but the connection does not appear in the dashboard, TLS interception is not actually happening — the traffic is bypassing the redirect. Check the iptables rules with sudo python -m ssl_inspect.iptables status and confirm that the client is not excluded by a RETURN rule.

Enable interception

These commands redirect TCP/443 into the sslsplit interceptor. Run as root. The install command is idempotent. 

# Redirect 443 → interceptor
sudo python -m ssl_inspect.iptables install

# Exclude the IDS host itself (adjust IP)
sudo iptables -t nat -I PREROUTING 1 -s <IDS_HOST_IP> -j RETURN

# Check current state
sudo python -m ssl_inspect.iptables status

# When done
sudo python -m ssl_inspect.iptables remove

How bypass works: the rules above are enforced at the iptables layer. Each enabled SNI pattern becomes a -m string match on the first packet of each connection; if it matches, the connection bypasses the redirect to sslsplit and reaches the real server directly. This means SNI bypass works even for certificate-pinned services, at the cost of the interception no longer seeing those connections. IP and CIDR rules apply the same logic but match on the source address instead of the ClientHello.
